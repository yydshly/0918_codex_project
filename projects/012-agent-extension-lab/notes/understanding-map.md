# 一图理解：借助插件与 Hook 开发产品

图的主线是：Agent 工作系统 → 开放的运行扩展点 → 插件接入与功能实现 → 定制产品体验。这里研究的是围绕 Agent 工作过程开发产品，不是 Agent 的理解、规划等通用能力分类。

## 运行扩展点

以下是接入环节的归纳，不是官方定义的“六大能力”，也不保证所有宿主开放全部入口：

1. 输入提交时：获取请求，按接口检查或补充，形成需求预检与模板助手。
2. 工具调用前后：观察调用、检查参数或处理结果，形成操作预览、脱敏与记录。
3. 权限与等待时：接收需要用户介入的信号，形成授权收件箱与人工接力。
4. 会话与代理状态变化时：观察开始、执行、结束等事件，形成多代理看板与像素办公室。
5. 输出与交付后：关联输出、产物和检查结果，形成验收与复盘产品。
6. 界面与通知入口：展示组件、交互控件与提醒，形成伴侣或等待小游戏；桌面窗口等能力还需要相应宿主支持。

## 实现方式

插件/Mod 组织可安装功能，Hook 接入运行环节；SDK 和日志提供其他事件来源；MCP/API/工具连接数据与动作；网页、IDE 和桌面承载界面。产品可能需要额外实现存储、调度与业务逻辑，不能认为一个 Hook 已经提供全部成品能力。

观察：真实事件 → 状态整理 → 界面与动画。
控制：用户操作 → 执行接口 → 真实回执。

显示状态不等于控制任务，停止事件不等于验收通过。游戏可以仅接收结束通知；防跑偏监督则可能额外调用模型作语义判断。两者使用的运行扩展机制与模型能力是不同维度。

## 可定制的产品方向

图中保留十类：需求与输入、知识与上下文、执行与质量、安全与治理、观察与成本、协作与调度、界面与陪伴、研究与内容、业务与集成、平台与生态。每类给三个例子，网页提供 40 项详情。这些是产品设想，不是上游已提供的四十个成品。

## 对我们的意义

借鉴插件和 Hook 的机制与案例，基于自己的需求开发产品，包括监控台、像素办公室、桌面伴侣、小游戏、效率助手、研究与验收工具、业务工作台等。结合现有研究工作，可以先做带进展、证据与验收的项目研究工作台，这是一个起步场景，并非唯一方向。

开发路径：选择需求 → 确认可用接口 → 做出最小产品 → 验证与分发。产品价值仍需通过真实使用验证。
