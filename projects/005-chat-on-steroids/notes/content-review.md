# 展厅内容审查与补充

审查日期：2026-09-18。固定版本：`2f9acf307189ed1f05bee0cdc97871fdcff1d8f5`，包版本声明 `2.1.14`。审查对象为本研究展厅及文字，不是上游运行效果。没有安装上游、连接账号或执行真实任务。

## 总体结论

原展厅的八类能力及“围绕 ChatGPT 会话组织任务”的定位基本成立。但网页节点上的“主会话与工作会话进行推理”存在位置歧义；“通过网页与扩展连接工具”也过度合并了两条独立路径。原内容缺少协议与执行责任的明确分工，没有充分突出复用现成对话环境这一设计价值。现已修正和补充。

## 逐项核对

| 项目 | 原问题或遗漏 | 修正与补充 | 固定版本依据 |
| --- | --- | --- | --- |
| 推理位置 | 网页节点写“进行推理”，容易误认为浏览器执行模型 | 区分本地工作台、真实 ChatGPT 网页会话、云端模型执行 | `AGENTS.md` §1–2 |
| MCP 调用方 | 工具路径简写为 ChatGPT → MCP，没有明确是远端服务调用 | 模型决定工具，ChatGPT 服务端经配置隧道访问本地 MCP；网页不是直接请求 localhost 的通用工具客户端 | `mcp/server.ts`、`docs/setup.md` |
| 扩展桥接 | 未说明扩展如何与本地通信 | 独立回环 Bridge；HTTP 命令、事件与回执；WebSocket 用于唤醒 | `bridge.ts`、`browser-wake.ts`、`extension/background.js` |
| 两个本地服务 | 容易把 MCP 和浏览器桥接视作同一入口 | MCP 对接云端工具调用，Bridge 对接扩展；有不同身份和访问边界 | `bridge.ts`、`mcp/server.ts` |
| 网页操作组合链 | 原图将 CoS 与扩展合在一个节点，省略本机桥接 | MCP 到本地后，经 Bridge → 扩展 → CDP → 目标网页；结果回传 | `tools-browser.ts`、`extension/browser-control.js` |
| 本地执行范围 | 所有工具都画在本地可能让人误解外部插件 | 文件 / 命令本地执行，原生桌面走系统辅助程序，插件可连本地或远端 MCP 服务 | `surfaces.ts`、`docs/plugins.md` |
| 输入递送 | 主流程图容易被理解为所有指令都模拟网页键盘发送 | 普通任务通常经网页；部分运行中纠正或收尾指令可随工具响应递送 | `session/input.ts`、`AGENTS.md` §1 |
| API 关系 | 仅强调真实网页可能被解读为整个项目没有 API 后端 | 主任务沿用 ChatGPT 会话，Goal / Loop 辅助决策可另配 API | `goal.ts`、`docs/setup.md` |
| 架构价值 | 过度集中在与 Codex 重复的能力清单 | 增加“复用现成对话环境 + 工具 + 外部编排”的模式，并与常见自建前后端 / 模型 API 方案比较 | `README.md`、`AGENTS.md` |
| 客户端 / 服务端概念 | 讨论中可能形成“这不是 C/S”的绝对判断 | 底层仍有 HTTP、云端服务和本地服务；差异是对话宿主与编排归属 | 上述整体结构 |

## 保留的有效结论

- 文件、终端、网页、原生桌面、多智能体、Goal / Loop、续接和插件的能力描述有源码依据。
- Core / Desktop / Plugins 为不同逻辑工具入口；不能把文件根目录限制当作 Shell 的系统沙箱。
- 多智能体组织真实 ChatGPT 工作会话，不等于调度多个 Codex CLI 进程。
- 续接不增加额度，不提供无限上下文；持久化会话记录不等于系统进程跨重启存活。
- 固定提交 manifest 要求 Chrome 125，README 的 116+ 描述滞后；仍以具体声明为准。
- 与 Codex 的比较是功能和架构层面的分析，没有效果、速度或成本优势的实测证据。
