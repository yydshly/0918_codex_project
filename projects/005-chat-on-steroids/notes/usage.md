# 使用场景与选型

## 对我们是否有直接价值

这个库的核心价值是**把网页版 ChatGPT 与真实本地环境关联，并围绕真实会话构建 Agent 能力**。它让既有聊天产品获得项目操作、工具执行、分工与任务延续的完整工作环境。对我们的启发是如何连接与组织这些部分；是否迁移日常工具，是另一个需要结合现有 Codex 能力判断的问题。

我们的工作是研究多个 GitHub 项目，产出可追溯文档和演示。Codex 已经能完成读取源码、运行工具、创建展厅等工作，因此不建议仅因“支持多 Agent / 终端 / 浏览器”再引入一套工作台。优先保留它作为 Agent 工程案例，只有出现明确缺口时再做小范围试用。

| 需求 | 本次判断 | 具体理由 |
| --- | --- | --- |
| 读代码、修复问题、跑测试 | 继续用现有 Codex | 工具能力重叠，迁移不直接产生收益 |
| 希望从 ChatGPT 网页使用本地项目与工具 | 值得试用 CoS | 它针对这条接入链路提供整体实现 |
| 给已有 Agent 增加网页操作 | 先看现有浏览器工具是否足够 | CoS 提供整套会话工作台，未必需要全部引入 |
| 学习多会话协作、恢复和消息递送 | 值得读源码 | 身份、持久化、回执与失败边界是关键工程问题 |
| 无人值守重要生产任务 | 先进行受控验证 | 本次未测试恢复、错误归属、实际权限和服务稳定性 |

## 三种能力组合示例

1. **本地 Web 修复**：读取登录代码 → 修改 → 测试 → 打开本地网站 → 表单操作 → 检查控制台和请求。展厅以此作为人工流程样本。
2. **开源项目并行研究**：主会话统一问题，工作会话分别分析架构、工具和运行前提，汇总时保留出处。需要人为划分共享文件的写入责任。
3. **跨软件制作任务**：先处理本地数据，再通过浏览器或原生桌面工具操作软件，必要时连接外部 MCP 插件。具体插件、登录、付费权限和平台兼容性需独立验证。

以上为基于能力推导的场景，没有在上游中运行。

## 如果未来安装上游

以下是阅读固定版本安装说明后整理的步骤，**尚未执行**。

1. 选择对应平台安装包，核验上游发布说明和校验信息。包版本声明不能替代安装包版本验证。
2. 在 Workspace 中配置实验文件夹，确认允许的工具。
3. 配置隧道，并在具备资格的 ChatGPT 工作区中添加 Core MCP 连接。
4. 在 Chromium 浏览器加载 companion 扩展，检查配对。研究版本 manifest 要求 Chrome 125 或更新版本，README 的较早要求存在滞后。
5. 若需要网页 / 桌面操作，再配置相应连接与权限；macOS 原生桌面还涉及系统授权。
6. 先运行最小任务，核对本地真实结果与工具历史，再逐步启用多会话、Goal 和续接。

## 最小实测计划（未执行）

| 问题 | 操作 | 应保留的证据 |
| --- | --- | --- |
| 文件工具是否真实生效 | 创建实验文本，再独立读取文件 | 工具结果与磁盘内容一致 |
| 终端能否持续交互 | 执行可控长命令，再轮询输出 | 进程会话 ID、输出与退出状态 |
| 网页驱动是否有效 | 操作本地测试表单，读取页面结果 | 操作前后截图、DOM 与请求 |
| 页面更新后旧引用是否拒绝 | 获取元素引用后刷新，再尝试旧引用 | 拒绝结果及新的页面身份 |
| 工作会话能否复用上下文 | 分派独立问题，完成后追问 | 主 / 工作会话身份与回传记录 |
| 长任务交接是否保留任务 | 设置明确任务和队列，再手动续接 | 交接文本、新旧绑定、未完成事项 |

只有实际完成相应实验后，才把那一项标为已验证。账号额度、提示内容、网络和模型选择应与结果一起记录。
