# 怎样参考这个前端工具目录

这个库的主要价值是帮助我们发现和选择前端辅助能力：设计 Skill、文档查询、设计资料连接、浏览器操作等。需求描述告诉助手要完成什么；所选 Skill 或工具提供具体方法、资料或操作渠道。仅阅读或克隆目录不会自动接入这些支持。

## 对我们的价值判断

围绕前端需求，从视觉风格、主题一致性、动效交互、用户体验与可访问性、设计稿衔接、框架与文档、浏览器验证及预览交付等角度，组织约束、方法和工具，指导 Agent 设计、实现与检查页面，以获得更符合需求的效果。

它提供的是 Agent 工作方式的指导与资源索引：Skill 和项目规则约束决策，外部工具提供资料与操作，浏览器反馈帮助修正。模型基础能力没有因此被训练或升级，效果仍取决于实际执行。

对我们而言，通用提示在现有 Agent 已能稳定完成时，额外价值可能有限；更值得保留的是项目特有的品牌与组件规范、真实资料接入和运行结果检查。

## 用同一个需求连起来

业务需求始终是：**帮我做一个咖啡品牌首页，展示品牌介绍和三款咖啡，点击“查看菜单”可到商品区域，手机上也能正常浏览。** 这段话交给 Claude Code，定义要完成的任务。

1. **从库里选资源。** 希望首页有合适的品牌风格，就从 Design Skills 章节找到 Frontend Design。
2. **配置资源。** 按该 Skill 的官方说明配置到 Claude Code，并确认本次任务能读取。目录本身不完成这一步。
3. **把资源用在刚才的需求上。** 在咖啡首页任务中说明：“请使用已配置的 Frontend Design Skill，先确定适合咖啡品牌的视觉方向，再实现首页。” Claude Code 此时结合业务需求和 Skill 中的设计方法来完成任务。
4. **检查是否实际起作用。** 核对任务是否读取了 Skill，再查看设计方案和实际页面。出现了工具名称、写了这句话，都不等于已经使用或已经改善效果。

关联发生在第 3 步：业务需求和所选资源共同参与同一个任务。这个库帮助找到资源，资源提供指导或工具支持，Claude Code 实际实现页面。它对我们的意义，是在现有前端流程缺少某种支持时，帮助找到并采用相应资源。

四项支持是按需选择，不必全部接入；下表均为原创使用过程示例，未进行模型生成效果对照。

| 同一个咖啡首页遇到的需要 | 从目录找到的资源 | 配置后，怎样用于这次任务 | 可核对的使用痕迹 |
| --- | --- | --- | --- |
| 希望品牌风格合适 | Frontend Design | 用设计指导组织字体、配色、商品布局 | Skill 读取记录、设计方案和实际页面 |
| Tailwind 主题写法不明确 | Context7 | 确认项目版本，查询后实现品牌配色 | 文档查询与返回内容、运行结果 |
| 已有咖啡首页设计稿 | Figma MCP | 提供设计节点，读取资料后实现 | 对应节点的设计信息和页面对照 |
| 需要检查手机上的菜单按钮 | Playwright MCP | 打开运行页面，点击菜单，检查跳转和溢出 | 实际操作、页面状态或截图记录 |

## 分清目录与实际工具

| 环节 | 提供什么 | 还需要什么 |

## 四种具体用途

### 页面风格普通：查设计 Skill

从 Toolkit 的 Design Skills 章节可以找到 Frontend Design 等候选项。Frontend Design 的独立指令文件提供设计与自查方法；配置到 Claude Code 并在任务中读取后，模型可以重复参考这些方法。

它补充的是设计指导，不是审美评分器。比如制作咖啡首页时，先组织适合品牌的字体、配色和商品布局，再实现。是否符合目标，需要查看实际方案和截图。我们核查了代表指令，未做启用前后的模型质量对照。

来源：[Toolkit Design Skills](https://github.com/wilwaldon/Claude-Code-Frontend-Design-Toolkit/blob/2a6d0958e6966e0003896f94ce5003466e89e91d/README.md#design-skills)、[固定版本指令](https://github.com/anthropics/claude-code/blob/31a3b00bef145a0393d9dbf840a98674fec07712/plugins/frontend-design/skills/frontend-design/SKILL.md)。实际安装应查看官方当前提供方式。

### 缺少框架资料：查文档工具

从 Docs & Context 章节可以找到 Context7。它有文档查询接口，支持通过 MCP 或 CLI + Skills 方式使用。接入后，助手可按库和问题取回相关资料，用于代码实现。

例如遇到不确定的主题配置写法，先查询与项目版本相关的资料。需要确认返回内容是否匹配，再运行代码。我们核查了官方说明，本展厅未调用 Context7 服务。

来源：[Context7 固定版本说明](https://github.com/upstash/context7/blob/dedb03d589e6e03e8fb5a2b858bd3c853ac6893e/README.md)。

### 需要读取设计稿：查设计资料连接

从 Design-to-Code Pipeline 章节可以找到 Figma MCP。其官方文档说明可向助手提供设计上下文，包括布局、组件和变量信息。使用前需核对受支持客户端、账户、文件权限及当前接入方式。

例如实现已有设计稿的咖啡首页，可先读取设计结构，再结合项目组件实现。连接和读取成功不等于已完成业务逻辑、响应式或视觉验收。本轮未连接 Figma 或测试还原效果。

补充来源：[Figma MCP 官方功能说明](https://developers.figma.com/docs/figma-mcp-server/)（2026-09-18 查阅，动态页面，无固定提交；与五份固定版本核心资料分开记录）。

### 页面缺少实际检查：查浏览器工具

从 Testing & Browser Automation 章节可以找到 Playwright MCP 等工具。按说明接入并提供可访问的页面后，助手可以执行浏览器操作、读取页面状态和截图。DevTools 则可补充网络与性能等诊断信息。

例如检查咖啡首页的手机菜单按钮，应真正打开窄屏页面、点击章节并观察结果。仅阅读代码不能据此声称界面已通过检查。本项目已使用 Playwright 脚本检查展厅，但没有因此证明 Playwright MCP 已经配置或验证。

来源：[Playwright MCP 固定版本说明](https://github.com/microsoft/playwright-mcp/blob/ea43eee0d95196ab31f7619b26f78d7b9c664286/README.md)、[本展厅检查记录](evidence/browser-qa.json)。

## 对我们到底有什么意义

我们已经能制作静态展厅并执行浏览器检查，因此不需要因为目录收录某个工具就重做现有流程。它的价值主要是节省寻找方法和工具的时间：需要某项支持时，帮助我们找到候选项，再回到官方来源核对。

可以按“确认缺口 → 核对官方说明 → 接入一个小任务 → 观察结果”采用。若现有方式足够，继续使用；若缺少设计资料或专项方法，再按需补齐。实际收益来自独立工具在具体任务中的使用，不来自把这份 README 加进仓库。

## 网页如何呈现

[这个库的实际价值](../demo/index.html#practice) 先展示不变的咖啡首页需求，再展示“目录选择 → 资源配置 → 与需求共同用于任务”的过程。四种资源可切换，每项都将接入前提、任务中的使用说明、实际补充的资料或操作、使用痕迹和固定来源相连。

独立的通用需求模板已移除。页面中的任务说明只解释所选资源怎样参与当前任务，不能代替安装、连接或授权，也不表示本轮已调用这些工具。
