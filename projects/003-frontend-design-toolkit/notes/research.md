# 能力与原理研究

研究日期：2026-09-18。对象为 Toolkit 的固定提交 `2a6d0958e6966e0003896f94ce5003466e89e91d`。本文区分来源事实、机制解释、研究建议和本地验证，不把第三方产品说明当作本轮运行结果。

## 1. 研究对象与结论

GitHub 文件树核查显示，该提交只包含 `README.md`。这是一个资源目录：将前端相关工具按设计、实现、检查和交付组织，并给出组合参考。没有包依赖清单、统一 CLI、运行服务或内置自动调度代码。将它克隆到本地，只会得到这份文档。

来源：[固定版本目录](https://github.com/wilwaldon/Claude-Code-Frontend-Design-Toolkit/tree/2a6d0958e6966e0003896f94ce5003466e89e91d)、[README](https://github.com/wilwaldon/Claude-Code-Frontend-Design-Toolkit/blob/2a6d0958e6966e0003896f94ce5003466e89e91d/README.md)。文件树、读取时间和内容哈希记录在 [sources.json](evidence/sources.json)。

**研究判断：它的价值在于识别能力缺口和选择工具。** 没有证据表明这是一个能够独立运行的设计系统，也不能从推荐列表推导出组合兼容性或设计质量提升。

## 我们的统一理解

围绕前端需求，从视觉风格、主题一致性、动效交互、用户体验与可访问性、设计稿衔接、框架与文档、浏览器验证及预览交付等角度，组织约束、方法和工具，指导 Agent 设计、实现与检查页面，以获得更符合需求的效果。

它提供的是 Agent 工作方式的指导与资源索引：Skill 和项目规则约束决策，外部工具提供资料与操作，浏览器反馈帮助修正。模型基础能力没有因此被训练或升级，效果仍取决于实际执行。

对我们而言，通用提示在现有 Agent 已能稳定完成时，额外价值可能有限；更值得保留的是项目特有的品牌与组件规范、真实资料接入和运行结果检查。

可把过程理解为：**前端需求 → 加入设计与实现约束 → Agent 使用模型和工具完成页面 → 依据真实结果检查与修正**。需求定义目标，指导约束做法，工具补充资料与操作，反馈决定是否继续修改。这个仓库本身整理这些资源和组合建议。

“希望获得更好的效果”是采用这些约束的目标，不是本轮已证实的效果。若要评价通用提示的额外收益，应固定模型、任务和工具条件，对比有无指导的结果；本研究没有进行该对照。

## 3. 原理：怎样指导 Agent 工作

### 3.1 设计 Skill：补充决策步骤

核查 Anthropic 的 `frontend-design/SKILL.md` 后，可以直接看到它以文字规定：理解具体产品、制定颜色和字体及布局方案、对照需求审查后再写代码，并在实现时自查。这些是模型工作时参考的指令。

因此，机制是改变输入上下文和工作步骤，而非修改模型权重。指令可能影响输出，但模型遵循程度和实际效果还取决于任务、模型及其他指令。若要证明“更好看”，需要固定任务与环境的对照评审。

来源：[Frontend Design 指令文件](https://github.com/anthropics/claude-code/blob/31a3b00bef145a0393d9dbf840a98674fec07712/plugins/frontend-design/skills/frontend-design/SKILL.md)。

### 3.2 项目规则与设计变量：补充一致性约束

本研究将它们分成两个层面：文字规则影响助手怎么修改项目；CSS 变量和组件复用影响浏览器实际渲染。只有组件引用共享变量，改动才会同步传递。文字要求本身不会重写旧页面。

展厅的本地实验使用一个 `--hue` 变量派生标题、标签和按钮样式，拖动滑块可以观察联动。这个实验验证了前端变量复用的机制，不能证明某个设计 Skill 更有效，也不代表整个色相范围都满足可访问性要求。

### 3.3 资料工具：补充当前任务所需的信息

Context7 官方文档列出库匹配和文档查询接口：先确定库标识，再按问题取回资料。其输出进入模型上下文，帮助代码生成参考相应用法。文档还明确，仓库不包含其私有 API 后端、解析和抓取引擎。

研究解释：这相当于工作中查资料；检索内容的质量、覆盖范围和版本匹配仍要核对。不能从“具备检索能力”推导出“生成代码不再出错”。

来源：[Context7 固定版本 README](https://github.com/upstash/context7/blob/dedb03d589e6e03e8fb5a2b858bd3c853ac6893e/README.md)。

### 3.4 浏览器工具：补充执行与观察

Playwright MCP 将浏览器操作通过工具接口提供给模型，可利用结构化可访问性快照理解网页并执行操作。截图可以补充视觉核查；结构化快照本身不足以判断版式美感。其官方文档也讨论 CLI + Skills 与 MCP 的适用权衡。

研究解释：工具负责执行操作、返回观察结果；模型或人解释证据并决定下一步。MCP 是连接方式，不会独立产生设计判断。浏览器检查只能覆盖实际执行的路径与条件。

来源：[Playwright MCP 固定版本 README](https://github.com/microsoft/playwright-mcp/blob/ea43eee0d95196ab31f7619b26f78d7b9c664286/README.md)。

## 4. 组合后的工作流程

以下为研究者归纳的流程，不是上游可直接运行的工作流定义：

```mermaid
flowchart LR
  A[人明确需求与验收条件] --> B[加载设计与项目规则]
  B --> C[按需读取文档和设计资料]
  C --> D[编码助手修改页面]
  D --> E[浏览器操作与截图检查]
  E --> F{达到验收条件?}
  F -->|仍有问题| D
  F -->|通过| G[交付或按需部署]
```

关键分工是：人定义目标和验收；模型规划与修改代码；工具读取资料、执行操作；人或模型依据实际结果继续修正。Toolkit 给出可选配件和组合线索，执行循环需要宿主助手与项目环境承接。

Web 中的六步演示以科研工具介绍页为例，点击步骤会切换预写的输入、动作、产出和限制，没有后台调用。发布地址只有真正部署成功并核对后才能填写。

## 5. 资料质量核查

### 5.1 Chrome DevTools 条目需要纠正

Toolkit 把 Chrome DevTools MCP 的作者列为 Anthropic，并展示带 `@anthropic-ai` 作用域的包名。核查官方仓库后，来源为 `ChromeDevTools/chrome-devtools-mcp`，配置示例使用 `chrome-devtools-mcp`。本研究未尝试安装 Toolkit 中的错误条目。

官方说明显示，该工具利用 Chrome DevTools 的诊断能力及 Puppeteer 自动化，可以读取网络和性能线索。它的职责偏向诊断，不能用“有浏览器访问”概括所有工具的差异。

来源：[Chrome DevTools MCP 官方固定版本](https://github.com/ChromeDevTools/chrome-devtools-mcp/blob/23b9a480010d803fc8962bb5d11017b1e2ad76b2/README.md)。

### 5.2 许可文本缺失

Toolkit README 的 License 小节链接 `LICENSE` 并标注 MIT，但该版本只有 README 文件。准确表述为“作者声明 MIT，独立许可文本缺失”，不应补造版权持有人或 MIT 全文。第三方工具适用各自的许可，不能因被目录收录就沿用目录声明。

### 5.3 动态数字不作为实测

推荐目录中的安装方式、工具接口、Stars 和上下文开销都可能变化。本轮没有统一环境下的测量，因此不复述 Token 节省比例或声称质量提升。版本固定使本轮结论可回查，不能保证未来安装方式仍然适用。

| 验证项 | 操作与预期 | 证据 |
| --- | --- | --- |
| 仓库定位 | 查询固定提交与递归文件树，确认文件组成 | [来源记录](evidence/sources.json) |
| 能力浏览 | 分类、关键词筛选、空结果、键盘选择与详情关联 | [浏览器检查](evidence/browser-qa.json) |
| 流程教学 | 六个步骤、前后边界、重置以及选择任意步骤 | 同上 |

| 展示兼容 | 桌面、平板、手机、深链接刷新、离线打开 | 同上 |

这里的“已验证”限于证据记录中的操作。没有运行 Claude、Context7 服务、Figma 或完整第三方工具链，没有比较启用 Skill 前后的生成结果。

编号路径检查发现，既有构建器会重写 README 链接，但未处理 `THIRD_PARTY_NOTICES.md`，导致复制到编号根目录后的许可链接指向错误位置。已为该文件补充同样的路径重写，并通过 [构建后浏览器检查](evidence/browser-built-qa.json)。[三项目回归记录](evidence/site-qa.json) 另确认既有两个展厅的关键路径仍可访问。本轮所有站点检查均在本地完成。

## 7. 后续怎样验证真正的质量提升

如需继续研究，应先选一个具体问题：例如同一真实页面任务，固定模型、输入内容、技术栈和时间预算，分别启用或不启用一种设计 Skill。保留提示、版本、输出、运行错误和截图，由不知道实验分组的人按内容清晰度、任务完成和一致性评审。随后再评估加入浏览器反馈的增益。

这些是后续实验建议，本轮未执行。不要把展厅中手写的小样板当成此类 A/B 实验。
