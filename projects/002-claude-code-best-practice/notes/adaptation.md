# 如何适配到自己的项目

[返回项目说明](../README.md)

以下内容是本研究根据源码模式提出的实施建议，不是上游已经提供并验证的业务工作流。

## 从需求到验收的对应关系

| 需要解决的问题 | 可以使用的组件 | 必须补齐的项目事实 |
| --- | --- | --- |
| AI 不知道项目怎样启动 | 项目说明 / 规则 | 可运行的启动、构建和测试命令 |
| 每次都要重复解释任务步骤 | Command | 输入、步骤、交接内容、停止条件 |
| 相同类型任务反复查阅资料 | Skill | 与当前项目匹配的文档、模板和例子 |
| 调查过程占用主任务大量上下文 | 专项 Agent | 清楚的任务边界与返回格式 |
| 完成或出错时需要提醒 | Hook | 事件类型、提醒方式与异常行为 |
| 需要浏览器或外部资料 | MCP | 具体服务、安装方式、权限和可用性 |
| 需要确保结果可交付 | 测试 / 构建 / CI | 可机器判定的通过条件，失败不能冒充成功 |

## 最小落地顺序

1. **先写项目说明。** 只收录真实有用的约定，例如技术栈、目录职责、准备环境、检查命令与交付条件。
2. **选一个高频任务。** 把重复口头要求组织成一条命令，先用一个真实样例跑通。
3. **拆出可复用技能。** 将操作知识、模板、样例留在技能目录，命令只负责协调。
4. **按需引入代理。** 有独立调查或专门上下文需求时再拆分；不要仅按职位名增加助手数量。
5. **补齐程序检查。** 测试、类型检查和构建应真实执行并保存结果；强制门禁应交给明确的程序机制。
6. **记录失败并改进。** 区分提示词遗漏、上下文缺失、工具失败与程序缺陷，修改真正起作用的层。

## 场景一：开发订单查询页

| 阶段 | 输入 | AI 的工作 | 可检查产物 |
| --- | --- | --- | --- |
| 澄清 | 用户需求 | 确认字段、分页、权限、空状态 | 明确验收样例 |
| 计划 | 当前接口与组件 | 阅读相关实现，规划本次范围 | 文件级改动计划 |
| 实现 | 计划及项目技能 | 编写页面、调用接口、增加必要测试 | 代码差异与测试输出 |
| 审查 | 实现结果 | 检查边界行为和相关影响 | 构建、测试、人工复核记录 |

可设计 `feature-flow.md` 协调步骤，`order-query/SKILL.md` 保存接口和组件约定。名称只是建议，未创建可执行的 Claude Code 配置。

完成条件示例：目标查询可用；无权限、无结果和请求失败状态符合要求；测试与构建通过。不要仅以“模型回复完成”作为验收依据。

## 场景二：修复重复提交缺陷

先保留失败样例；专项调查返回根因假设与源码证据；最小修改后增加能复现原问题的回归检查。最后重新执行原触发步骤，并检查合法重试没有受影响。

适合用 Agent 隔离繁杂调查，用 Skill 保存测试方法；是否增加 Agent 应取决于上下文与重复任务的实际收益。不要为一个简单修改机械地引入多个助手。

## 场景三：研究开源仓库

固定 commit 与许可证 → 追踪关键入口 → 最小实验 → 文档与交互展示 → 更新索引。可将来源清单、实验记录和结论边界做成技能模板。

本研究的对应产物为：来源 SHA-256 清单、Hooks 隔离实验、中文笔记、本地教学展厅与网页 QA。完整 Claude Code 代理流程未验证，展示中保留了这一限制。

## 不应直接照抄的部分

- 天气示例固定到迪拜坐标；它用于解释分工，不是通用天气系统。
- 作者个人状态栏、提示文字及权限偏好应按项目实际需要替换。
- Hooks 提示音仅提供通知。若改成格式化、质量检查或阻断，要按目标事件协议实现并验证。
- 对 `allowedTools` / `tools` 等字段，核对当前运行环境识别的格式；提示词里宣称受限不代表权限真的受限。
- 业务失败和网络失败要有清楚的输出规则；必要的重试、状态恢复与幂等应由实际程序承担。

## 与本研究仓库的关系

本仓库当前使用 `AGENTS.md` 维护自己的协作约定。上述概念具有参考价值，但 `.claude` 文件格式面向 Claude Code，不因阅读本项目而自动应用到当前工具。迁移到其他 AI 编程工具时，应使用对方支持的指令、技能与权限机制。
