# KOReader：能力、效果与对我们的意义

## 项目定位

KOReader 是面向电子墨水屏优化的完整多格式阅读器。其重点是将不同文档引擎、可调排版和设备适配组合起来，让电子书、论文、扫描资料在小屏设备上更容易阅读。

本项目采用 v2026.07.1 作为研究版本。下文是文档与源码分析，未进行本机或阅读器实测。

## 能力与阅读效果

| 能力 | 具体支持 | 预期阅读效果与条件 |
| --- | --- | --- |
| 多格式 | EPUB、FB2、MOBI、TXT、HTML、DOC、RTF、CHM；PDF、DjVu；CBZ / CBT | 多类本地资料集中阅读；支持格式不等于每个复杂文件都能完美显示 |
| 排版 | 字体、字号、行距、页边距、样式覆盖、断词 | 流式文档随屏幕和字号重新换行、分页 |
| 固定页面 | 裁边、缩放、分栏、重排、倾斜校正 | 减少阅读大页论文时频繁拖动；表格、公式、跨栏图需检查 |
| OCR | 对没有文字层的页面做识别 | 辅助选词和文字获取，取决于文档质量与语言数据；重排不等于 OCR |
| 阅读导航 | 目录、搜索、书签、章节与页面浏览 | 更容易定位、回顾长书中的内容 |
| 摘录与学习 | 高亮、笔记、导出、StarDict 词典、维基百科、翻译、生词学习 | 边读边查、积累摘录；在线查询需要网络，本地词典需要词典文件 |
| 内容接入 | Calibre、OPDS、Wallabag、RSS | 获取或管理书籍与文章；需要相应来源、配置或服务 |
| 进度与统计 | 跨 KOReader 设备阅读进度同步、阅读统计 | 在已准备好同一文档的设备间接续阅读；不是整本书自动同步 |
| 墨水屏适配 | 局部与完整刷新、对比度、无动画界面、按键与手势 | 平衡显示质量、交互速度和残影；具体效果由设备决定 |
| 扩展 | Lua 插件、配置、用户补丁、OTA，另有 SSH / 终端等工具插件 | 可定制工作流；不同平台能力和依赖存在差异 |

来源：[固定版本 README](https://github.com/koreader/koreader/blob/v2026.07.1/README.md)、[用户指南](https://koreader.rocks/user_guide/)。

## 关键机制

Lua / LuaJIT 组织交互、阅读逻辑及插件，通过原生绑定或 FFI 使用 C/C++ 库。CREngine 处理流式排版；MuPDF 与 DjVuLibre 处理固定页面；K2pdfopt 在需要时做版面分析与重排。设备层负责输入、绘制和屏幕刷新。

扫描页可以先变成图像，再按区域裁切与重新排列。因此扫描件重排不一定需要先识别所有文字；OCR 是识别文字的另一项工作。

来源：[koreader-base](https://github.com/koreader/koreader-base)、[开发指南](https://koreader.rocks/doc/topics/Development_guide.md.html)、[刷新机制](https://koreader.rocks/doc/modules/ui.uimanager.html)、[K2pdfopt 原理](https://www.willus.com/k2pdfopt/)。

## 大文件如何打开：我们的理解

支持处理较大的文档，但“支持格式”不等于“任意大小都能流畅打开”。实际表现由文件内部结构、页面复杂度、图片分辨率和设备内存共同决定。本轮未找到可以对所有格式、设备统一承诺的容量上限，也未做大文件实测。

| 类型 | 打开与显示机制 | 大文件的主要压力 |
| --- | --- | --- |
| PDF 等固定页面文档 | 打开文档并读取结构，按需要渲染页面；优先复用缓存；启用预渲染时准备后续页面 | 复杂页面、高清图片解码、缩放和引擎内存 |
| EPUB 等流式文档 | 解析内容、样式并计算排版；CREngine 使用磁盘缓存加快再次打开 | 首次解析与排版、复杂 CSS、调整字号后的重新计算 |
| 扫描书、高清漫画 | 页面主要由图片构成，需要解码、缩放和绘制 | 像素尺寸和解码后的内存可能比压缩文件大小更关键 |
| 开启重排、OCR 或倾斜校正 | 普通文档处理之外增加版面分析、识别或图像处理 | 额外计算与内存；低性能设备可能明显变慢 |

**PDF 不需要先把整本书渲染成图片。** 固定页面渲染路径会检查缓存，缓存未命中才打开所需页面并绘制；如果整页结果超过缓存接收能力，且调用方提供显示区域，会尝试只渲染该区域。按页渲染不代表引擎只占一页内存，文档结构、图片解码等仍有额外开销。

**缓存预算不等于整个应用的内存上限。** 文档缓存根据可用内存及配置计算预算，通过 LRU 策略淘汰最近较少使用的内容；其他引擎、解析与图像缓冲仍会占用内存。

**EPUB 的部分重新排版有条件。** 分章节组织的文档有利于局部重新计算；如果整本书都装在一个巨大 HTML 文件中，修改字号等设置可能需要重新计算整本书。因此不能将 EPUB 简单理解为“只读取当前页”。

例如，假设一张 6000 × 8000 像素扫描图按原尺寸解码为每像素 4 字节，仅像素数据就约 192 MB，尚未计算其他开销。这是内存计算示例，不是 KOReader 的实测占用，也不意味着它总会按该方式解码。

对我们的启发是学习“按需渲染、有限缓存、预渲染、磁盘缓存”的组合，而不是根据文件 MB 数推断阅读是否流畅。目前无需继续安装或制作测试样本。

依据：[固定版本页面渲染](https://github.com/koreader/koreader/blob/v2026.07.1/frontend/document/document.lua)、[文档缓存](https://github.com/koreader/koreader/blob/v2026.07.1/frontend/document/doccache.lua)、[页面预渲染](https://github.com/koreader/koreader/blob/v2026.07.1/frontend/apps/reader/modules/readerhinting.lua)、[CREngine 接口](https://github.com/koreader/koreader/blob/v2026.07.1/frontend/document/credocument.lua)、[用户指南中的性能说明](https://koreader.rocks/user_guide/)。

## 使用平台与本次决定

官方列出的运行环境包括 Android、Linux，以及 Kindle、Kobo、PocketBook、reMarkable、Cervantes 等电子书设备。具体机型需要检查安装指南。开发者也能在 Linux / macOS 中运行模拟环境，这不等于官方提供各桌面平台即装即用的安装包。

已核查 v2026.07.1 官方发行资产，没有 Windows 原生安装包。本机原有 WSL，但为了这次体验继续安装运行依赖不符合用户当前意愿，因此取消安装。

## 对我们的实际意义

以下是结合当前 Windows 使用环境与开源项目研究目标作出的判断，不是上游的产品承诺：

- **当前直接使用价值有限。** 仅为看看效果而增加一套 Linux 运行依赖，当前收益不高。保留研究资料即可。
- **有电子书设备或 Android 长阅读需求时再评估。** 特别适合重视排版自由、经常读论文、扫描书和本地资料的场景。
- **工程研究价值明确。** 可参考多文档引擎的统一接口、Lua 与原生代码分工、插件扩展方式、低性能设备上的渲染与缓存设计。
- **复用应围绕具体需求。** 若未来做阅读器或墨水屏产品，再深入代码；目前不需要把整套应用接入现有仓库。
